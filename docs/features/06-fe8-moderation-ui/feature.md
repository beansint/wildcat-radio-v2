# Feature: Moderation UI  (Issue #8)

- **Branch:** `feature/8-moderation-ui`  ·  **Milestone:** `M4`  ·  **Spec:** docs/features/011-moderation, docs/features/012-moderation-log-read (paired backend slice)
- **Repo(s):** frontend

## Problem & why

M4's backend (#9 the moderation engine, #44 the log-read slice) shipped strikes/mutes/bans, reports, watch-flags, appeals, reinstatement requests, and the staff-audit/broadcast-activity logs — but none of it was reachable from the browser. Moderators had no queue to triage reports, no user-search to act on a handle, no way to read either log; listeners had no way to see their own standing or appeal a strike; custodians had no escalation-review surface. This slice is the UI over the already-typed orval client for all five surfaces.

## Acceptance criteria (numbered, testable)

- **AC-1:** `/mod/queue` renders a triage stack across four queue-entry types (reports, watch-flags, appeals, reinstatement requests) with a segmented-tab filter (All/Reports/Flags/Appeals/Reinstatement, each showing a count) and per-card one-click actions ("Looks fine"/Dismiss, approve/deny reinstatement) plus a Strike action that opens a dialog (severity-override toggle) before issuing a strike.
- **AC-2:** `/mod/users` supports debounced handle/name search and lists results with class chip (CAMPUS/GUEST), a status pill (Active/Muted/Banned), and an "N of 3" strike count; row actions cover Strike, Mute (confirm → 24h), Ban, and Force-rename.
- **AC-3:** `/mod/logs` exposes two tabs — broadcast activity (episode/time-in/time-out lifecycle events from the 5-point instrumentation) and staff audit (append-only actions incl. queue-issued strikes) — each paginated and filterable by date range.
- **AC-4:** `/profile/standing` shows the signed-in user's own strikes, active mute (with reason + local-time expiry converted from UTC), and ban state, and lets them submit a written appeal against an active strike/mute.
- **AC-5:** `/admin/escalations` (CUSTODIAN only) lists pending appeals/reinstatement requests across three tabs and lets the custodian record a decision (uphold/reduce/overturn) with a mandatory written response.
- **AC-6 (RBAC edge):** a LISTENER hitting any `/mod/*` route is redirected to `/`; anyone other than CUSTODIAN hitting `/admin/escalations` is redirected to `/`; an unauthenticated visitor to any of these routes is redirected to `/login?next=<path>`.
- **AC-7 (end-to-end acceptance):** a moderator issues a strike from `/mod/queue` → the struck user's `/profile/standing` shows the strike with reason + expiry → the user submits an appeal → the custodian records a written response on `/admin/escalations`, which is then reflected in the affected user's standing (strike removed/mute cleared on Overturn).

## Scope

- **In:** the 5 pages/routes above; consuming the orval-generated client (`src/lib/api/endpoints/moderation`, `src/lib/api/endpoints/users`) against the backend OpenAPI contract from #9/#44; RBAC route guards; the strike/mute/ban/force-rename action dialogs; the two-tab logs reader; the appeal submission + custodian decision flows.
- **Out:** any backend contract change (owned by #9/#44 — this slice only consumes it); free-text reasons on one-click Mute/Ban actions (fixed reason, still audit-logged — see Edge cases); message-content lookup for a report's `targetMessageId` (no endpoint exists); persisting a written response on the reinstatement-approve variant (`approveReinstatement` only accepts `{approve}`).

## Contract

- **Routes:** `src/app/(staff)/mod/queue`, `src/app/(staff)/mod/users`, `src/app/(staff)/mod/logs`, `src/app/(app)/profile/standing`, `src/app/(staff)/admin/escalations` (per AGENTS.md route-group convention: `(staff)` = moderator/custodian chrome, `(app)` = authed-user chrome).
- **Data/API:** consumes the typed client generated by `orval.config.ts` from the backend's `openapi.json` (docs/features/011-moderation + 012-moderation-log-read):
  - `GET/POST /api/mod/queue*`, `/api/mod/users/:id/action` (strike/mute/ban/force-rename) — `src/lib/api/endpoints/moderation`, `src/lib/api/endpoints/users`.
  - `GET /api/mod/audit`, `GET /api/mod/logs/broadcast` — `src/lib/api/model/staffAuditPageDto.ts`, `broadcastActivityPageDto.ts`.
  - `POST /api/mod/reports/:id/resolve` — one-click "Looks fine"/Dismiss.
  - `GET /api/users/me/standing` → `MeStandingDto` — `/profile/standing`.
  - Appeals/reinstatement/escalation decision endpoints — `src/lib/api/model/{appealDto,reinstatementRequestDto,escalationsDto}.ts`.

## Edge cases

- `/mod/queue`: empty state per tab (no seeded data) renders a typed empty state, not a blank list; switching tabs never shows more cards than "All".
- `/mod/users`: search input is debounced (no request-per-keystroke); status pill reflects Active/Muted/Banned precisely, including the "Muted until…" long-label case.
- `/mod/logs`: date-range filter refetches both tabs independently; staff-audit tab surfaces actor by id where the DTO carries no handle (known limitation, not a bug).
- `/profile/standing`: good-standing (0 strikes) renders distinctly from a populated standing; submitting an empty appeal is blocked client-side with a `role="alert"` error.
- `/admin/escalations`: Overturn removes the underlying strike and clears any active mute; the written-response field is mandatory for all three decision types.
- RBAC: all three guard cases (LISTENER on `/mod/*`, non-CUSTODIAN on `/admin/escalations`, unauthenticated) must redirect, never render-then-hide.
- One-click Mute/Ban actions send a fixed reason string (no free-text field in the confirm dialog) — matches the prototype's one-click intent; the reason is still written to `StaffAuditLog`.

## Notes / decisions

- This is a pure consumer of the already-typed #44 contract; no backend changes are made or expected as part of this slice.
- Reviewer/actor identity columns (staff-audit `Mod`, escalations `resolved By`, broadcast `Triggered by`) show raw ids where the underlying DTO carries only an id, not a handle — the *subject* of each row is always resolved to a handle (enriched DTOs); resolving the actor too would need a backend DTO change, tracked as a future enhancement, not a bug in this slice.
